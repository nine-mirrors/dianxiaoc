## 1.2 闭环缺口（逐条带证据）

### 缺口 A｜整改留证闭环是「假按钮」——最高优先级

**代码证据**（`DiagnosisView.vue:238-240`）：
```js
if (action.includes('已处理')) {
  toast.success('已标记处理，下次复查时留证对比')
}
```
问题清单里的「标记已处理」**只弹了一个 Toast**，不写库、不改状态、不生成回执、不关联照片。评委点下去看到绿色提示，但刷新后什么都没发生——这是最容易被当场戳穿的一处：**演示动作有、结果没有**。

**更深一层**：PRD 需求池 #8「S2 店 48 → 80 (+32) 整改复查」看起来是闭环核心证据，但它是 `stores.json` 里的静态字段（`prevScore: 48, lastScore: 80`），**不是本次演示跑出来的**。也就是说：整个"闭环"目前靠**预先摆好的静态数据**支撑，链路上没有一个环节是用户操作产生的。

**结论**：业代能"开方"，但不能"收方"。闭环缺 3 件事：①整改单执行回执（含回传照片）②任务状态回传 ③复查对比。

### 缺口 B｜任务闭环只有「下行」，没有「上行」——第二高优先级

**代码证据**：
- `stores/tasks.ts:40` 定义了 `markDone(id)` → 调 `PATCH /api/v1/tasks/:id`
- 全站 grep：**`markDone` 零调用点**；`useTasksStore` **零使用**（任何 .vue 都没 import）

即：**经理下派任务 → 业代看到待办 → 业代无法标记完成 → 经理端也看不到任务完成状态**。
`GET /api/v1/tasks`（接口 #14）和 `PATCH /api/v1/tasks/:id`（#16）后端都实现了、前端 API 层都封装了，**但没有任何页面用它们**。

同时 P5 看板**没有"我派的任务"列表**——经理只知道"我派了个任务"，不知道"他做没做"。这在真实业务里是致命的：**管理动作没有回执，就不叫管理闭环**。

### 缺口 C｜订货单数据流「只写不读」——店主端下单是个死胡同

**代码证据**：
| 环节 | 状态 |
|---|---|
| `POST /api/v1/tickets`（P4 生成整改单/订货建议） | ✅ 后端落库 + `broadcast('ticket:new')` |
| `POST /api/v1/tickets`（P6 店主一键订货） | ✅ 同上 |
| 前端订阅 `ticket:new` | ❌ **零订阅**（只有 `TodayRouteView` 订阅了 `task:new`） |
| `GET /api/v1/tickets`（单据列表接口） | ❌ **后端根本没有这个接口** |
| 业代端「待接单」入口 | ❌ 不存在 |
| 经理端「区域订货单/补货量汇总」 | ❌ 不存在 |

**结论**：店主张大姐按下"一键订货"后，单据进了 SQLite 就再也没人看见。P6 成功页写着"业代李强将在 2 小时内与你联系"——但**李强的界面上没有任何地方能看到这个单**。这是队长问的"订货数据流去哪了"的准确答案。

### 缺口 D｜经理看板三处「看起来能点、其实没数据」

### 缺口 E｜数字口径三处打架（评委翻车高危）

| 位置 | S3 补货方案 | S3 风险损失 | 冲突点 |

### 缺口 F｜P2 概览的平均分不随本次诊断变化

后端 `visits/today`：`avgScore = doneStores.map(r => r.store.lastScore)` 取的是**门店档案里的历史分**，不是本次诊断得分。演示时业代刚给 S3 做完诊断返回 P2，概览的「平均健康分」纹丝不动——**闭环在数据上不显形**，削弱了"我刚才的诊断有产出"的感知。

## 明确表态：如果只能再做 2 件事，做哪两件？

### 🥇 第一件：**整改执行闭环（#1）**

**理由（按权重排序）**：
1. **它是当前唯一的"叙事断点"**。产品定位是"诊断 + 方案 + **闭环**"，评委的五个维度里"业务价值 30%"是权重最高的，而业务价值最直接的证明就是"整改完有没有变好"。现在能诊断、能开方，但**方开完就断了**。
2. **它是评委必问的第一个问题**。演示完 P4，评委不问"整改完怎么复查"几乎不可能。而当前答案只能是"这是预置的演示数据"——这句话一出，闭环的分数直接归零。
3. **它同时消灭三个缺陷**：假按钮（缺口 A）、任务无上行（缺口 B）、S2 静态对比无法归因。
4. **有真素材支撑**：`S2/cold_before.jpg` 已存在，补上"整改后拍照"这一环就能形成真实的前后对比。
5. **可复制潜力得分**：真正的闭环 = 诊断→执行→复查→再诊断，可无限循环，这个故事对评委讲得通。

### 🥈 第二件：**订货单三端打通（#2）**

**理由**：
1. **它是"死数据"，评委自己就能发现**。店主端刚按下"一键订货"，成功页写着"业代 2 小时内联系你"——然后评委切到业代端，**找不到这个单**。这是产品逻辑的洞，不是功能的缺失。
2. **它是"业务价值"最直接的证据链**：店主自助 → 生成订单 → 业代确认 → 经理看到区域补货量。这是**唯一一条贯穿三个角色的数据流**，讲"生意怎么在系统里流转"只能靠它。
3. **成本低**：后端已有 `tickets` 表和 `createTicket`，只需加一个列表接口 + 两处 UI。
4. **补上后可复制性叙事**：不只是一个巡店工具，而是**连接品牌方、业代、终端的补货中枢**——这才是可复制潜力的正确表述。

### 为什么不做其他项？
- **#5（AI 自动展开）**：0.5 天、零风险、纯增益，但它只是"让已有功能被看见"，不解决任何逻辑断裂。**应该做，但它是"送分题"不是"决胜题"**，前两项做完还有时间就顺手做掉。
- **#8（MCP 可视化）**：AI 深度加分强，但它是"锦上添花"——闭环断裂是"致命伤"。**先救命，再添花**。
- **#4（前后对比）**：视觉最强，但它是 #1 的**展示层**。#1 做完 #4 几乎免费（同一个后端数据），所以**不要单独排期，做 #1 时顺手做**。
