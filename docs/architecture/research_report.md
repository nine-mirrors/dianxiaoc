**检验结论（本报告判断，标注为「推断」并给出风险）**：

- **第一档「打卡软件＝去过+拍了」**——成立，无争议，行业普遍如此。
- **第二档「AI 识别产品＝识别+看板」**——成立，B1–B4 四家的公开能力边界确实主要停在识别与看板/合规报告。
- **第三档「我们＝诊断+方案+闭环，是 Agent 不是工具」**——**方向正确，但作为「差异化」被高估**：截至 2026-10，海外头部（Trax / ParallelDots / Effie）与国内头部（ImageDT）均已公开宣称闭环与 Agent 化，其中 Trax 甚至拥有线下执行力量做到物理闭环。**因此「有没有闭环」已不构成差异化，「闭环做得多深、过程多可解释」才可能是。**

**对本项目有利的一面（同样有依据）**：五家标杆中，**没有一家公开披露其评分模型的权重来源或销量损失的量化推导公式**。本项目的六维权重（D1 §7.1）+ `forecast.js` 的 Holt→单列日均→z·σ·√L→建议补货量推导链（D16）+ 风险卡的 `derivation` 多步算式（D32 §diagnoses.json S3），在「过程可解释」这一点上确实走在公开资料之前。**推断**：这才是可以被现场演示证明、且不易被追问击穿的锚点。风险在于——该判断基于「公开资料未披露」这一消极事实，若某家标杆在付费材料或非公开方案中已有类似推导，本结论会被削弱（见 §5.1 R-01）。

### 2.5 建模口径的外部证据（对应 Q4 / 种子 S4）

#### 2.5.1 排面（facing）变化对销量的影响——Drèze / Hoch / Purk (1994)

| 项 | 内容 | 来源 |
| --- | --- | --- |
| 文献 | Xavier Drèze, Stephen J. Hoch, Mary E. Purk, "Shelf management and space elasticity", **Journal of Retailing, Vol.70, No.4, pp.301–326, 1994** | SR-13（论文 PDF）/ SR-14（期刊目次页） |
| 方法 | 在真实超市做的一系列**现场实验**（field experiments），不是问卷也不是实验室 | SR-13 |
| 核心结论（原文摘要） | 「location had a large impact on sales, whereas changes in the number of facings allocated to a brand had much less impact **as long as a minimum threshold (to avoid out-of-stocks) was maintained**」——**位置影响大；只要保住避免缺货的最低排面阈值，排面数变化对销量影响很小** | SR-13 摘要 / SR-14 |
| 效果量级 | 货架集定制化带来销售额与利润约 **4%** 的小幅增益；货架重组织带来 **5–6%** 的变化 | SR-13 摘要 |
| 二次转述（独立来源交叉验证） | INSEAD 工作论文对该文的转述：「returns on increasing the number of facings increased rapidly between 3 and 15 square inches and leveled off above that number… virtually no additional sales potential of increasing the number of facings beyond their current level」——**排面收益存在明显饱和点，边际收益递减** | SR-15 |

**对冲突 X3 的证据倾向（重要，但不替架构师裁决）**：

X3 的两种口径是：PRD 的**单一弹性系数 0.35**（D1 §7.3）vs 代码的**三档严重度系数 0.7 / 0.95 / 1.4**（D31 §RISK、§severityOf；D32 fixture 实测 S1/S2后=0.7、S3/S4=0.95、S2_BEFORE/S5=1.4）。

1. **「排面-销量关系是非线性的」这一前提，有 1994 年的现场实验支持**：边际收益递减（SR-15）意味着「缺口越大，单位缺口的损失越大」——这与代码按缺口占比分档（≤20%→0.7、20–50%→0.95、>50%→1.4）的**单调递增结构方向一致**。
2. **「超过阈值的绝对量级」无公开文献支持**：1.4 意味着缺口 >50% 时，日损失 = 日均动销 × 缺口占比 × 1.4，缺口 60% 时相当于损失日均动销的 84%。Drèze 的原文说的是「空间弹性很低（low space elasticities）」，而非「接近或超过 1」。**因此 0.7/0.95/1.4 这组具体数值在本轮调研中未找到任何公开来源，本报告标注为「业务假设，未验证」**。
3. **PRD 的 0.35 同样无外部来源**，且从 D2 §5.5 的自洽验算看，0.35 与成品数字 3.9 瓶/天本身就不自洽（`11 × 37.5% × 0.35 = 1.44`，而非 3.9）。
4. **资料摘要自身的优先级声明**（D1 §7.4「演示数据以 fixture 为准，公式用于现场/新增照片的动态计算路径，两者允许 ±3 分偏差」）与代码实际走向一致。

**结论倾向（建议，非裁决）**：**保留代码的三档口径（0.7/0.95/1.4），但必须把它显式标注为「业务假设」并写进 derivation，而不是沿用 PRD 的 0.35。**理由：① 分档结构有非线性文献支持，单一系数没有；② 资料摘要已声明以 fixture/代码为准；③ 0.35 与成品数字不自洽，回退到 0.35 会同时制造 X3 与 X4 两处新的不自洽。**关键前提**：必须在 P4 风险卡的推导依据里写明「该系数为业务经验值，非实证估计」，否则答辩时会被追问击穿（见 §5.1 R-03）。

| VLM 计数错误的结构性成因 | GPT-4V 的回答数高度依赖物体在图中的位置，且出现「翻倍/翻四倍」的系统性错误（正确 4 个时答 8 或 16），成因被归因于高分辨率切片重叠 | SR-21（LLaVA-UHD, arXiv 2403.11703） |
| 密集/小目标场景错误类型 | MLLM-CompBench 归纳 GPT-4V 四类错误：颜色区分、**小或远处物体计数**、**拥挤场景中识别目标**、焦外细节；GPT-4V 在该基准上 68.6% vs 人类 86.5% | SR-18（arXiv 2407.16837） |
| 专用检测模型在零售基准上的实际水平 | SKU-110K 上 YOLOv8 mAP@[0.50:0.95] **59.7**；RPC 数据集上 YOLOv8 **76.2**、YOLOv4 74.1 | SR-17（PMC 零售 SKU 模型对比表） |
| SKU-110K 数据集背景 | 由 Goldman 等人为 CVPR 2019《Precise Detection in Densely Packed Scenes》创建，**数据集由 Trax Retail 提供**；11,743 张货架图、170 万+ 标注框、平均每图约 147 个密集商品、单类别 | SR-16（Ultralytics 官方数据集文档） |
| 头部厂商已产品化的「混合架构」 | 阿里云视觉智能开放平台「陈列检测」：先由**多模态大模型（MLLM）在整图上检测每个商品的边界框与初步名称**，再用**客户专属 SKU 向量库做相似度召回**覆盖初步名称，输出逐商品结构化结果 | SR-21（阿里云官方产品文档） |

**关键事实（对本项目直接相关）**：阿里云「陈列检测」的产品化架构与本项目 `vision.js` 的「VLM 出框 → 与 fixture 参照量比对 → 超阈值则回退 fixture 坐标」是**同一架构范式**——都是「通用 MLLM 做粗定位/粗语义 + 客户专属真值库做精对齐」。区别只在于：阿里云用向量召回做 SKU 名对齐，本项目用按层阈值做坐标对齐。**这条是本报告对决策点 T1 最重要的正面证据**：本方案的方向已被头部厂商产品化验证。

| T3-A | 一致性 2：与代码（D31）与 fixture 实测（D32 各店 elasticity 0.7/0.95/1.4）冲突，回退需改代码 + 改 fixture + 改 derivation，等于制造新的不自洽；可解释性 2：D2 §5.5 已证明 0.35 与成品数字不自洽（`11×37.5%×0.35=1.44` ≠ 3.9），无法自证 |
| T3-B | 一致性 5：与代码完全一致；演示可靠性 4：数字沿用 fixture 权威值，现场不会翻车。**方法论加分项**：分档单调递增的结构与「排面收益边际递减」的现场实验结论方向一致（SR-13/SR-15）。**扣分点**：0.7/0.95/1.4 三个具体数值无公开来源，Drèze 原文强调的是「空间弹性很低（low space elasticities）」，而非接近或大于 1（SR-13） |
| T3-C | 可解释性 5：在 T3-B 基础上，把「该系数为业务经验值、非实证估计」写进 `derivation`，并同时给出 PRD 0.35 口径的对照数字。这是唯一能扛住「1.4 怎么来的？」这一追问的方案 |

**结论**：**采用 T3-C**。即**保留代码的三档口径，但补可解释标注**。本报告**不替 `system-architect` / `business-architect` 裁决 X3**，仅给出证据倾向：分档结构有文献支持，具体数值无文献支持，两者必须分开陈述。

### 3.8 决策点 T4（命题 B4）：实时推送

| 候选方案 | 落地成本(0.15) | 演示可靠性(0.30) | 答辩可解释性(0.20) | 工程复杂度(0.15) | 一致性(0.10) | 扩展潜力(0.10) | 加权总分 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| T4-A WebSocket `/ws`（任务下行）+ SSE（AI 逐 token）双通道（**现状**） | 4 | 5 | 4 | 3 | 5 | 4 | **4.25** |
| T4-B 全 WebSocket（AI 流式也走 WS） | 3 | 3 | 3 | 3 | 2 | 3 | **2.90** |
| T4-C 全 SSE + 轮询（任务用轮询取） | 4 | 2 | 3 | 4 | 2 | 2 | **2.80** |

**打分依据**

| 方案 | 关键依据 |
| --- | --- |
| T4-A | 演示可靠性 5：两条链路各司其职，SSE 的 EventSource 自带自动重连与断点续传（Last-Event-ID），WS 负责双向心跳与定向投递（D18）。**行业事实支撑**：SSE 已成为 LLM 逐 token 流式的事实标准——OpenAI、Anthropic、Google Gemini 及几乎所有 LLM 供应商的流式 API 都采用 SSE，Vercel AI SDK / OpenAI SDK / Anthropic SDK 底层均消费 SSE（SR-27）；而双向高频互推才是 WebSocket 的适用场景（SR-27/SR-28） |
| T4-B | 一致性 2：AI 流式改走 WS 需重写前端 `streamSse` 的 `text/event-stream` 手工解析（D30 §index.ts SSE）与两个端点；可解释性 3：与「SSE 是 LLM 流式事实标准」的行业惯例相悖，评委若熟悉该惯例会质疑选型 |
| T4-C | 演示可靠性 2：轮询无法保证「经理下派 → 业代秒级弹出」这一**闭环关键证据**（D1 §4 P5 成功态标注「整个 Demo 讲闭环的关键证据，必须验证通过」），轮询必然引入可见延迟 |

**结论**：**保留 T4-A（现状双通道），行业证据支持其合理性。** 唯一需注意的实现约束：HTTP/1.1 下浏览器对单域名有 6 个并发连接上限，每个 SSE 流会长期占用一个（SR-27/SR-28）；本项目 SSE 端点仅 2 个且为短生命周期（生成完即关闭），实测不构成瓶颈，但部署文档应写明「不要用 HTTP/1.1 反向代理长时间挂起 SSE」。

### 3.9 决策点 T5（命题 B5）：数据层

| 候选方案 | 落地成本(0.15) | 演示可靠性(0.30) | 答辩可解释性(0.20) | 工程复杂度(0.15) | 一致性(0.10) | 扩展潜力(0.10) | 加权总分 |

**打分依据**

| 方案 | 关键依据 |
| --- | --- |
| T5-A | **有官方场景背书**：SQLite 官方《Appropriate Uses For SQLite》明确列出「**Stand-in for an enterprise database during demos or testing**」——用 SQLite 作为演示/测试场景下企业级数据库的替身，是其官方推荐用法之一（SR-25）。同时官方把「应用与数据在同一台机器、低写入并发、内容远小于 1TB」归为 SQLite 适用区（SR-25/SR-26）。本项目三端单机同库、5 张表、128 家门店，完全落在该区间。零依赖还直接服务于「换机克隆少一个失败点」的目标（D22 §不使用 dotenv 的同源理由） |
| T5-B | 演示可靠性 3：引入独立数据库服务 = 新增一个「没起来就白屏」的失败点，与 D14 §P0 建目录修复所体现的「启动链路越短越稳」原则相悖；一致性 2：5 张表 + 3 处迁移逻辑需整体重写（D14 §建表/§索引与迁移） |
| T5-C | 演示可靠性 1：重启丢数据，跨角色闭环（经理下派 → 业代收到 → 回执 → 看板回流）直接不成立，而 D3 §T05.3 明确该闭环写入「SQLite 真库」 |

**结论**：**保留 T5-A（现状）**。**但必须处理一个版本风险**：`node:sqlite` 自 v22.5.0 引入、稳定性标注为 1.1（Active development），在 **22.5.0–22.12 需要 `--experimental-sqlite` 标志**才能使用，22.13.0 及以后无需标志，Node 24/25 起进入 Release Candidate（SR-24/SR-23）。而本项目 `启动说明.md` 只写了「Node.js ≥ 22.5」（D4 §一 环境要求），**未提及该标志**——若复现环境落在 22.5–22.12 区间，后端会直接起不来。详见 §5.1 R-04。
